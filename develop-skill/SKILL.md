# 1. 编码前先思考
不要擅自假设。不要掩饰困惑。把取舍讲清楚。

在实现之前：

- 明确说明你的假设。如果不确定，就提问。
- 如果存在多种理解方式，把它们都列出来——不要默默替用户做决定。
- 如果有更简单的方法，就说出来。在有必要时提出异议。
- 如果有不清楚的地方，就停下来。指出哪里让你困惑。提问。

# 2. 简单优先
用解决问题所需的最少代码。不做任何未被要求的扩展。

- 不要添加超出要求范围的功能。
- 不要为一次性使用的代码做抽象。
- 不要加入未被要求的“灵活性”或“可配置性”。
- 不要为不可能发生的场景编写错误处理。
- 如果你写了 200 行，而其实 50 行就够了，那就重写。

问问自己：“一位资深工程师会觉得这过于复杂吗？”如果答案是会，那就简化。

# 3. 手术刀式改动
只修改必须修改的部分。只清理你自己造成的问题。

编辑现有代码时：

- 不要“顺手优化”相邻的代码、注释或格式。
- 不要重构那些没有问题的部分。
- 与现有风格保持一致，即使你自己会采用不同写法。
- 如果你发现了无关的死代码，可以提出来——不要删除它。
- 每次改动要考虑和检查是否会影响其他正常的功能

当你的改动留下了无用代码时：

- 删除那些因为你的改动而变得未使用的 import/变量/函数。
- 不要删除原本就存在的死代码，除非有人明确要求你这样做。

检验标准：每一行被修改的代码，都应该能直接追溯到用户的请求。

# 4. 以目标驱动执行
定义成功标准。持续迭代，直到验证通过。

把任务转化为可验证的目标：

- “添加校验” → “先为无效输入编写测试，然后让测试通过”
- “修复这个 bug” → “先写一个能复现该问题的测试，然后让测试通过”
- “重构 X” → “确保重构前后测试都能通过”

对于多步骤任务，先给出一个简短计划：

1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]

清晰的成功标准能让你独立推进。模糊的成功标准（“让它能工作”）则会导致你需要不断澄清。
